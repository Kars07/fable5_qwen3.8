Nemotron Terminal RL Dataset Structure, Verification Protocol & Reward Shaping Report
====================================================================================================

### 🔍 1. Dataset & Decision State Architecture

Every record in the dataset represents a stateful decision point at turn T in a multi-turn Linux terminal task:

1. messages (Observation & Terminal History up to Turn T):
    • [0] System Prompt: Operating instructions for the AI terminal agent.
    • [1] Initial User Prompt: The natural language operational problem description.
    • [2...N] Past Interaction: Alternating previous assistant actions and real terminal stdout/stderr outputs.

2. reference_completion (Ground-Truth Target Decision):
    • Reasoning (<think> ... </think> or JSON "analysis" + "plan"): Diagnoses current terminal buffer and formulates a concise, step-by-step plan.
    • Action: JSON structure with "commands" array containing "keystrokes" ending with '\n' and "duration".
    • Task Complete: Boolean signal ("task_complete": false during ongoing turns, true upon verified final fix).

### 🛡️ 2. Cheat-Proof Correctness-Gated Reward Function Architecture

To prevent reward hacking (such as fake edits, premature submissions, or passive read-only discovery loops),
the reward function in rl_pivot_terminal/taskset.py uses a strict correctness-gated scoring protocol:

┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                                 REWARD FUNCTION SCORE BREAKDOWN                                  │
├────────────────────────────────┬───────────────┬─────────────────────────────────────────────────┤
│ Tier / Component               │ Max Weight    │ Verification Criteria & Anti-Hacking Guard      │
├────────────────────────────────┼───────────────┼─────────────────────────────────────────────────┤
│ 1. Base Structure & Reasoning  │ +0.20         │ • +0.10: Valid <think>...</think> or JSON CoT   │
│                                │               │ • +0.10: Valid JSON schema & command boundaries │
├────────────────────────────────┼───────────────┼─────────────────────────────────────────────────┤
│ 2. Ground-Truth Correctness    │ +0.50         │ • Evaluates keystroke match against reference   │
│    (Dominant Learning Signal)  │               │   fix/test commands in expected_answer_raw.     │
│                                │               │ • Exact command match: +1.0x (full +0.50)       │
│                                │               │ • Target token / binary match: +0.5x            │
│                                │               │ • Random/dummy commands score +0.00.            │
├────────────────────────────────┼───────────────┼─────────────────────────────────────────────────┤
│ 3. Submission Integrity Gate   │ +0.30 to      │ • If task complete expected & model submits:    │
│    & Anti-Gaming Penalty       │ -0.50         │   - Verified fix (correctness >= 0.5): +0.30    │
│                                │ (Penalty)     │   - Fake / premature submit: -0.50 (PENALTY)    │
│                                │               │ • If intermediate turn & model sets false:      │
│                                │               │   - Intermediate action progress: +0.30 * corr  │
│                                │               │   - False premature submit: -0.50 (PENALTY)     │
└────────────────────────────────┴───────────────┴─────────────────────────────────────────────────┘

Total Reward Range: [-0.30, +1.00]
• Full Correct Solution + Verified Submit: +1.00
• Intermediate Diagnostic Turn (with valid next action): +0.70 to +0.90
• Fake Edit + Premature Submit Gaming Attempt: -0.30 to -0.50 (Guarantees negative GRPO advantage)

### 🔄 3. Multi-Turn Trajectory Progression Model (max_turns = 6)

In the upgraded multi-turn execution harness, episodes progress through distinct operational stages:

Stage 1: Exploration & Diagnosis (Turn 1)
  - Model runs diagnostic commands (ls, cat, ps, netstat, config inspection).
  - Emits: "task_complete": false.
  - Runtime executes commands and feeds back real terminal logs.

Stage 2: Active Modification & Code Patching (Turns 2 - 4)
  - Model applies code fixes (sed, cat << EOF, python3 -c, patch, vim/nano scripts).
  - Emits: "task_complete": false.
  - Runtime applies filesystem mutations and returns output.

Stage 3: Verification & Compilation (Turns 4 - 5)
  - Model compiles binaries (make, go build, cargo build) and runs test suites (pytest, benchmark.sh).
  - Emits: "task_complete": false until test assertions pass.

Stage 4: Goal Confirmation & Verified Submission (Turn 5 - 6)
  - Model inspects passing test logs and output artifacts.
  - Emits: "task_complete": true.
  - Verifier validates end-to-end correctness and awards full +1.00 completion reward.
